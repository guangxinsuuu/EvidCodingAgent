# 22 · 后续扩展路线与系统完成标准

规划状态：`PLANNED`；实现状态：`NOT_STARTED`。阅读前置：[00](00-overall-plan.md)、[09](09-seeded-defects.md)、[18](18-evaluation-and-pilot.md)。本章区分首期选定的发布验证切片与后续能力，不把全部远期需求塞进首期。主场景是稳定版本→新功能候选→针对性发布验证→有效缺陷Finding才Coding；已知事故修复保留为另一种入口。

## 1. 四次正式回顾

| 回顾点 | 必须回答的问题 | 合理结论 |
| --- | --- | --- |
| G1实验台完成 | 真实栈是否稳定？屏障与Observer能否可信区分健康/缺陷？ | 继续Runtime，或先修环境/观察能力 |
| G3主展示切片完成 | 新功能候选是否先验后修？无seed能否不误改？修复是否保留新增功能？ | 进入受控交付/价值对照，或先补功能Oracle与执行入口 |
| G4受控交付完成 | 当前候选、批准、远端对象与CI是否一致？故障恢复安全吗？ | 进入试点评估，或修复执行/权限缺口 |
| G5价值评估完成 | 独立Verifier带来的质量收益是否覆盖成本、时延和人工成本？ | 推广、限定场景、调整策略或保留简单流程 |

任何“停止扩展”的决定都保存理由和证据；它可能是正确的工程结果。

首期V3.4为自有健康对照；正确V4新增十一月政策与tool schema v2，同时支持十月续费事件。首轮固定LLM/Worker，latest-only与wrong-date作为独立人工变异；后续模型、Prompt、Worker和handoff升级分别评估。标签不代表上游发布或真实线上历史，首条公开案例只用于校准。

客服语义质量、自动对客发送和真实退款分别设后续门槛：缺人工校准rubric、数据、统计/重复策略和批准阈值时，只声明合成草稿范围。SUP-05工单revision、全面恢复矩阵、handoff、企业Connector及多语言按21逐项准入；不能因后续延期而删除当前已承诺的mandatory。

## 3. 扩展任务必须写清的九个字段

每个后续工作包建立一份小规格，至少包含：问题与用户、当前证据、目标行为、非目标、依赖、接口/数据变化、正反验收、成本与运行责任、退出/回退策略。然后拆成一个会话能完成的检查点。

例：请求“加RAG”不足以立项。可落地的表述是“指定项目文档的精确引用召回不足；先以带ACL的全文检索建立基线，评估embedding是否提高目标任务召回且不增加撤权泄露”。无需为了检索先改写整个修复平台。

## 4. 怎样判断整个系统搭建完成

| 完成范围 | 必须具备 | 证据锚点 |
| --- | --- | --- |
| 本地原生实验台 | 合成客服SUT、真实LLM/工具、独立观察、SUP Oracle、清理 | G0/G1，03–09 |
| 受控验证与修复平台 | Run/Attempt/Check/Candidate/预算；Release先验后修与Incident入口、可信Final | G2/G3，10–14 |
| 增量发布主展示 | GenAI manifest、需求差异、新政策/工具功能、适用SUP与历史兼容、正确/变异、公平规划对照 | 06/08/09；G3完成切片，18/G5评估 |
| 可审阅交付 | 隔离资格、用户审批、准确PR/head/CI、恢复 | G4，15–17 |
| 可评估试点 | 真实模型记录、公平对照、成本/人工时间、缺陷归因 | G5，18 |
| 可运营服务 | 企业身份、运行指标、备份、恢复、升级、值班与退役 | 19适用项 |
| 企业数据与多业务能力 | 对应来源和业务Profile实际验收 | 20–21逐项资格 |

“整个系统完成”必须带范围。例如Native Pilot完成可以同时注明“企业文档接入未启用、未生产部署”；不会因有一个功能未做就否定已完成范围，也不会把局部结果扩大为全系统保证。扩展时逐项核对[93 完整v3检查映射](93-v3-acceptance-coverage.md)中的延期项，新数据路径按[94](94-data-flow-and-retention.md)准入；延期不能计作PASS，门槛未达到就不宣称企业生产完成。

完成判定还要分清三个轴：`task_mode=RELEASE_VERIFICATION|INCIDENT_REPAIR`、`repair_policy=DISABLED|ON_VALIDATED_FINDING`、`completion_mode=FINAL_ONLY|DRAFT_PR_CI`。Release没有有效候选资产Finding可以不调用Coding；只要最终新功能候选相对冻结stable base有变化，仍为CHANGED并按完成模式结束。NO_CHANGE要求完整输入相对任务base未变且任务满足；不能把“零修复”当“零版本变化”。把V4全回滚到stable或删除功能以通过旧检查，不满足发布任务。

## 5. 需要长期维护的资产

- **规范**：Owner、版本、摘要、批准/撤销、适用性与迁移。
- **实验目录**：模板、参数、Oracle、健康/反例、观察盲区和flaky处置。
- **环境目录**：源码/依赖/镜像、SUT数据库/Redis、Prompt/语料/检索/工具/model配置、代理、资源、权限、清理。
- **任务集**：稳定到新功能候选的seed/no-seed发布组、已知事故、健康、自然缺陷、环境错误、合同歧义；授权stable/candidate差异与QA私有正确参考实现分开，开发集与holdout分离。
- **证据和副作用账本**：原始结果、候选谱系、批准、远端事实、未决与保留策略。
- **运行手册**：告警Owner、恢复步骤、值班交接、升级/退役流程。

运行日志中的新假设先进入待评审Backlog，不直接更新ACTIVE合同或隐藏验收答案。

## 6. 何时引入更复杂基础设施

先用真实数据定位限制：容器启动慢就改环境复用与隔离策略；依赖下载慢就治理可信缓存；Final昂贵就优化已批准检查实现与资源，不减少强制覆盖；Planner重复无效实验就改停止/排序策略。

只有单宿主排队、故障域或组织分工问题被测量后，才评估分布式调度、Kubernetes或其他工作流框架。迁移时以现有故障矩阵和Evidence协议作为兼容要求，而不是重新定义“成功”。
