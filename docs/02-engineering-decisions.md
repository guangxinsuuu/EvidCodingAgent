# 02 · 工程取舍：异步推理发布验证

状态：`ML_MIGRATION_IN_PROGRESS`。通用 TS 骨架和 file-lab 原语已有实现；ML 真实栈、独立观察、Python Verifier 和正式发布仍按章节实施。前置：[01 架构](01-system-architecture.md)；技术决定与业务批准分开记录于 [91](91-decision-log.md)。

## 1. 选择标准

先验证一个有现实变更风险的闭环：稳定推理服务升级模型、预处理与 Worker 后，旧任务是否仍使用其约定的输入和模型，结果是否可靠完成。框架数量、Agent 数量、跑了多少无关测试都不是目标。保留已有治理积累，替换业务适配层，并用独立证据判断新版本。

## 2. 技术栈与代价

| 选择 | 理由 | 代价 / 限制 | 改变条件 |
| --- | --- | --- | --- |
| TypeScript + pnpm 控制面 | 现有配置、协议、实验账本与 Docker 原语可复用 | 需运行时边界校验；不能用编译代替授权 | 有明确治理服务语言需求 |
| FastAPI + Redis Streams + ONNX Worker SUT | 真实异步图片分类链，规模适合做版本与恢复实验 | 新模板，不具备已证明的企业生产历史；上游缺每任务模型绑定等能力 | 真实业务或必要能力超出模板边界 |
| Python LangGraph 独立 Verifier | 与 ML 实验生态匹配，规划循环可读 | 增加 Python 锁文件与跨语言协议；当前尚未实现 | 同预算评测无收益则保留固定策略 |
| 版本化 JSON Schema 边界 | TS/Python 共用字段、错误和引用协议 | 两端编解码需黄金样本，不能各自发明状态 | 协议变更走版本迁移 |
| PostgreSQL 治理权威 + 显式事务 | 可审查租约、预算、审批、Outbox 与幂等 | 第10章起实现；当前 file-lab 不能代表多 Worker | 根据容量证据优化，不能把通知队列升级为权威 |
| EGAP Redis/BullMQ 仅通知 | 与业务 Redis 分离，通知可重建 | 多一个运维组件；不得混用凭据、队列和清理命名空间 | 测量显示可以简化 |
| 本地内容寻址 ArtifactStore | 先建立可追踪来源、模型、输入与证据 | 不自动提供跨机持久性、访问隔离和保留治理 | 多宿主或企业数据引入对象存储 |
| CPU ONNX + 合成图片 | 先验证调度、模型身份、结果与故障语义 | 不证明 GPU 性能或真实分类质量 | 经批准的数据、硬件及 ML-07 目标具备 |
| 文件型模型/预处理 manifest | 最小模型内容身份，不先依赖注册平台 | 自有业务扩展必须实现并独立验证 | MLflow/Feast 能解决已测得的管理问题 |
| Codex CodingProvider | 在可信 Finding 后修复允许路径 | 模型凭据、候选构建、验收与发布必须隔离 | 用同一接口公平比较其他 provider |

镜像、Python/ONNX/Redis 版本以来源和构建核验锁定，不使用 `latest` 或开发机恰好安装版本。上游依赖声明与本项目已验证工具矩阵是两份事实。

## 3. 为什么保留 EGAP，却停止订单主线

保留 control-plane、contracts、domain、artifacts、LabLedger、单机锁和受限 DockerHost，因为它们处理实验身份与权限，不依赖订单语义。Eventuate adapter、Java 构建配置与来源证据留作明确的历史范围，不参与默认 ML 源码准备、运行或验收。切换业务不抹掉旧失败和真实完成记录，也不把旧编译结果包装成新系统已通过。

旧 AAA 的 lease/epoch、精确批准、observe-first 与 Console 思路仍可参考。模拟 Kafka/CI、内存 Repository 或 VM 沙盒结果不能成为新 ML 系统的恢复、安全或发布资格。复用仍是“理解原语 → 明确新接口 → 最小移植 → 新范围重验”。

## 4. 独立验证的实际边界

Coder 可写批准的业务路径和局部开发测试。它不能写 trusted Oracle、隐藏数据、采集证据、预算账本或 Final Gate。Verifier 可按规则提出实验与补充证据要求，不能改业务真相、签发自身发布批准或自由执行 shell/SQL。

独立性由规则来源、输入视图、运行身份、挂载、网络和证据写权共同建立。第二个 LLM 或同一进程中另一个类本身不构成独立验证；也不要求必须换一家模型供应商。Agent 负责选择和解释，受保护的确定性 Runner/Oracle 负责裁决。

候选 Python build backend、安装脚本、测试和模型加载器都能执行代码。构建域无宿主 socket、模型 API key、治理/发布凭据；可信宿主仅加载经摘要核验的工件和审核过的固定拓扑。首期使用自有合成数据与单租户测试宿主，不声称敌意多租户隔离已经获证。

## 5. 先做哪些检查，为什么

第一风险是 ML-02：任务在排队时经历模型别名切换，Worker 却延迟解析为新模型。它直接展示版本发布引入的异步一致性问题。ML-01 补充成功状态与结果持久化顺序，防止“HTTP 接受/最终有一个状态”被当作业务完成。

ML-03/04/05/06 按 feature、重复投递、恢复和 schema 能力进入验收。发布承诺包含哪项，就必须有对应有效检查；能力不足只能阻断或缩小明确声明的发布范围，不能默默略过。ML-07 涉及批准的样本、标签、切片、统计与硬件条件，另建工作包，不用旧新预测完全相同替代质量评价。

Verifier A 选择现有模板，B 调整批准参数，C 仅提出新实验并经 QA/安全审查晋升。首期实现 A+B。历史 Stable 覆盖帮助排序和界定差异，当前 Candidate Final 的强制项不可由模型削减。

## 6. 必须先验证的技术点

- **模型执行身份**：Worker 实际加载的模型字节与预处理 revision 能否独立观察；仅返回自述版本字段不能通过 ML-02。
- **实验屏障**：排队暂停、模型选择时点与结果写入持有是不同能力；必须有精确任务选择、实际命中和释放回执，不能把 `sleep` 当可信屏障。
- **持久性承诺**：Redis AOF `everysec`、任务/结果 TTL 与进程重启不能证明零数据丢失或无限保留。Owner 需明确故障模型与期限。
- **候选不可绕过**：运行代码不能访问控制屏障、Observer 管理口、隐藏答案或证据写口；能力通过后才可登记资格。
- **跨语言摘要**：规范化、排序、Unicode、字节编码和浮点处理须版本化；模型输出的浮点容差是合同字段，不临时放宽。
