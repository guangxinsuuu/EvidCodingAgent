# 00 · 总体计划：把设计变成可验证的系统

状态：`ML_MIGRATION_IN_PROGRESS`。通用控制面骨架、实验账本与 Docker 适配器已有实现；异步 ML 的真实基线、独立 Oracle 和发布闭环尚未通过。本章是路线与验收约定，不是业务合同批准记录。阅读前置：[手册使用方法](README.md)。

## 1. 最终要交付什么

我们的主场景是**基于稳定版本的新版本发布验证**：工程师提交稳定基线、已有功能变更的候选、需求变化与历史覆盖，系统分析本次影响，把测试预算优先分配给受影响且缺证据的行为；发现可信缺陷后才按授权调用Codex修复，再独立验收。用户能看到“为什么测这些、哪些未测及原因、发现了什么、减少了多少测试与人工成本”，而不是只看到测试数量或模型生成的补丁。

主业务改为 **Async ML Inference Release Verification（异步机器学习推理版本验证）**。以固定FastAPI/Redis Streams/ONNX图片分类服务和合成图片为 SUT：客户端提交任务，队列交给 Worker，Worker 加载特征和模型，持久化预测结果后完成任务。信用风险评分可作为未来领域包装；首期只承诺已审查的真实输入与推理能力，不把模板假称生产风控系统。

主 Demo 使用自有实验 Stable V3.4→Candidate V4.0：自有健康基线先建立可查询且可独立核实的模型执行身份；V4新增模型B、preprocess/schema v2并保留批准v1兼容，同时重构Worker。验证版本切换期间任务是否仍使用提交时固定的模型/预处理。先以“排队期间别名切换，Worker 错用新模型”校准 ML-02，再验证正确新功能候选和带回归候选。ML-01 补充结果先持久化、状态后成功的因果要求。

V3.4/V4.0 是自有实验的**服务发布标签**，不是上游版本、模型版本或已证明的线上历史。模型用独立的 `model_artifact_digest` 与不可变 revision 标识；数据、特征 schema、预处理和推理运行时也各有身份。人工缺陷标为 `SYNTHETIC_MUTATION`，不得指称上游已存在缺陷。旧 Eventuate 源码、构建和实验记录保留为历史，不能转为 ML 的健康证据。

两种入口共享同一平台：`task_mode=RELEASE_VERIFICATION`先验证已提交候选；`INCIDENT_REPAIR`处理已明确的缺陷，可在修复授权下先Coding。`repair_policy=DISABLED|ON_VALIDATED_FINDING`单独控制改代码权限，验证任务可以完全不运行Coding。

首个包含代码变更的完整交付终点：**当前候选通过适用的新功能、关键安全与发布层级回归验收，经过精确人审，发布到指定自有Fork的Draft PR，且可信CI核对准确head。** FINAL_ONLY评测止于验收。V4.0没有发现缺陷、Agent没有修复，也可正常验收成功；NO_CHANGE仅指最终完整输入相对任务冻结比较基线未变化且满足任务，不能等同“没有调用Coder”。合并、生产部署和事故恢复各有后续Gate。

“实施手册可作为逐章基础”不等于“完整满足企业生产标准”。[93 v3验收映射](93-v3-acceptance-coverage.md)逐项列出原L1/L2/L3目录、实施阶段、缺口与延期理由；[94 数据流转与保留](94-data-flow-and-retention.md)登记跨系统区域、期限、访问者和企业数据准入条件。后续生产结论必须由目标范围的实际证据支持，不能仅靠本计划或某个首期子集通过。

## 2. 三个交付层级

| 层级 | 能演示什么 | 必须留下什么 | 不能宣称什么 |
| --- | --- | --- | --- |
| 原生实验台 | 真实任务、队列、模型工件、结果与可信实验屏障；健康/缺陷对照 | 环境清单、原始观察、适用 ML 检查结果、清理回执 | Agent 修复有效、平台发布可靠 |
| Release Verification Pilot | 真实新增功能候选、变更影响、针对性探索、可选修复、Final及按需交付 | Stable/Candidate身份、需求变化、测试选择理由、漏报/成本/人工投入与发布证据 | 多租户生产能力、已替代绝大多数QA工作 |
| Enterprise / Production | 企业身份、实际连接器、生产适用业务、部署和恢复 | 真实环境资格、权限否定测试、SLO/DR、业务交接 | 由本地 Demo 自动继承这些结论 |

03–18是首期主线；09先完成单缺陷校准，再增加最小发布任务切片，返回06/08补新功能合同及检查后接入G3/G5主Demo。21记录该最小切片与后续完整扩展的边界，不要求等19–21全部完成才演示增量发布。19–21的运营、企业连接及广泛业务强化仍分别排期。

## 3. 为什么按这个顺序建设

可信验证需要明确规则，规则需要可观察事实，事实需要真实可复现环境。先接模型会把环境故障、测试问题和业务缺陷混在一起。因此第一段先做实验台，再做可恢复执行，最后接入 Agent 与发布。

稳定版本的历史测试用于确认对照身份、规则和已有覆盖，不按每个新候选机械重跑全部历史套件。首次建实验台、环境/依赖漂移、历史证据失效或需要因果对照时，才按明确理由复核相关基线。历史PASS不证明新候选正确；每个最终候选仍执行批准的mandatory及变更适用检查。开发顺序中先实现Coding适配器，不代表Release任务必须先调用它。

```mermaid
flowchart LR
  E[03-05 环境与真实基线] --> C[06-09 契约与可信实验]
  C --> R[10-11 持久化和恢复]
  R --> A[12-14 发布验证与可选修复]
  A --> S[15 安全与平台资格]
  S --> P[16-17 人审及发布]
  P --> V[18 公平评估]
  V --> O[19-21 运营与企业扩展]
```

## 4. 每一段的可演示结果

| Gate | 对应章节 | 实际交付 | 通过条件 |
| --- | --- | --- | --- |
| G0 可复现环境 | 03–05 | 工具链锁、运行清单、真实健康场景 | 固定版本能启动、端口可发现、依赖可解释、环境可清理 |
| G1 可裁决实验 | 06–09 | 批准范围、Observer、实验屏障、ML Oracle、seed 对照 | 健康版本通过，变异版本在目标规则上失败，坏观察器不能通过 |
| G2 可信执行 | 10–11 | PostgreSQL Run/Check/Outbox、租约、预算和恢复 | 真实 DB、多 Worker 下故障恢复不丢权威状态、不盲重做未知动作 |
| G3 发布验证与修复闭环 | 09发布切片、12–14 | Stable/ChangeSet/新需求、可信外部候选、针对性Planner、可选Coding及Final | 正确新功能版可无修复通过；含回归版被发现并按权限处理；不能回退稳定版删功能骗过验收 |
| G4 受控交付 | 15–17 | 隔离资格、审批界面、Action Gateway、PR/CI 对账 | 无越权、审批绑定准确对象、未知发布先查远端、CI 匹配 head |
| G5 试点价值 | 18 | 同候选/同预算的发布QA对照、漏报误报、首个Finding时间、测试成本与人工分钟 | 在质量底线不降的前提下验证效率收益；修复收益另账，不预先宣称替代QA比例 |

早期 05 的基线事实只用于环境/观察校准；G1 才能把它提升为对应范围的 `BASELINE_VALIDATED`。DRAFT 合同可在明确授权的隔离实验中调试，但不能假造正式批准或进入正式发布 Gate。

## 5. 首期业务范围

首期合同目录为 ML-01 结果持久化后成功、ML-02 模型版本一致、ML-03 特征快照一致、ML-04 重复投递一致、ML-05 Worker 恢复、ML-06 输入/输出 schema 兼容、ML-07 质量与性能。**目录不等于已实现能力或全量强制集合。** 当前优先建设 ML-02 与 ML-01 的可裁决实验，随后按来源能力补 ML-03/04/05/06；ML-07 必须有批准数据集、质量指标、统计方法与性能条件后另行启用。

每个发布候选的验收集合由批准范围决定：强制 smoke/关键安全检查、变更专项、适用兼容性、发布层级回归。若需求承诺了幂等、崩溃恢复或 schema 升级，即须具备对应检查后才能放行，不能因尚未实现 Oracle 就从验收删除承诺。未知影响扩大检查或交 QA 复核。

新版模型预测可以合法不同于旧版；判断依据是版本绑定、输入语义、批准质量门槛，不是逐项要求旧新预测相同。上游没有的模型注册、特征存储、恢复与幂等能力必须明确作为新增业务实现，不能靠适配器伪造。首期不强制引入 MLflow、Feast、训练流水线或 GPU。

## 6. 实施方法：一篇文档可以分多次会话

每次只完成一个可检查的纵向片段，例如“提交 CheckIntent 并写入 outbox”，而不是同时搭建所有服务。

1. 读取当前章节、前置结果和 `92-progress-and-session-log.md`。
2. 确认本轮范围、输入与预期证据，检查当前源码实际状态。
3. 实现最小可演示行为，补对应正例和失败窗口测试。
4. 检查实际结果，保留首次失败与物理重试记录。
5. 真实结果保存到reports/artifacts并在会话交付中说明；只有用户明确允许修改docs时，才更新92、91及其他文档。未获允许时给出拟更新内容，不能因“按章实现”自动改手册。

文档里列出的未来接口和命令是实现合同。下一轮应先创建对应代码，不能把命令名称当作已存在工具。本轮交付手册不会自动执行模型、连接企业账号或发布远端对象。

## 7. 共同完成标准

- 行为可实际运行；正向结果与关键反例都可解释。
- 代码、环境、契约、检查及证据版本可定位。
- 重试、取消、超时、缺权限和资源清理有明确出口。
- 涉及真实业务规则的决定有 Owner 记录；设计作者不能代填批准人。
- 文档中的预计行为与运行观察分开；测试跳过项可见。
- 需要独立身份的组件已按权限边界部署，不能只用类名表示隔离。
- 本阶段所有事实写入报告；下一阶段只复用身份完全匹配的有效结果。

## 8. 学习重点与取舍

你会依次掌握：异步业务因果、可执行合同、独立 Oracle、持久化状态机、故障恢复、受控模型工具、证据聚合、精确审批及外部副作用对账。学习目标是能解释“为什么这样做、什么情况下会失败、用什么证据说它成立”。

采用 TypeScript 治理平台、Python 异步推理 SUT 与 Python LangGraph 规划器，通过版本化 JSON 协议交接；第一版单租户、单 Run 测试宿主，仍保留 tenant_id 和角色边界。首期不引入 Kubernetes、向量数据库、自由生成测试代码或多个模型调度层。何时值得增加它们见 [02 工程取舍](02-engineering-decisions.md) 和 [22 后续路线](22-future-roadmap.md)。
